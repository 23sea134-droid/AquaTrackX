4.5.1 Captive Portal Configuration

**Access Point Mode:**
When the device cannot connect to a saved WiFi network (first boot or connection failure), it automatically enters Access Point (AP) mode:

• SSID Format: "AquaTrackX_{DEVICE_ID}" (e.g., "AquaTrackX_WM001")
• No password authentication (open network for easy access)
• IP Address: 192.168.4.1 (standard captive portal address)
• Broadcast interval: 100ms (for quick device discovery)
• Timeout: 180 seconds (3 minutes) before restart if no configuration

**Connection Process:**

```
User Actions → Device Responses:

1. User taps "Save" with credentials
   → Device writes to ESP32 NVS
   → Returns "Configuration saved" message
   
2. Device automatically reboots
   → Attempts connection to configured network
   → LED blinks blue during connection attempt
   
3. Connection Success:
   → LED turns solid green
   → Device obtains IP via DHCP
   → Displays IP on OLED screen
   → Connects to Firebase
   → AP mode disabled
   
4. Connection Failure:
   → LED turns red
   → Retries 3 times (10-second intervals)
   → If all attempts fail, returns to AP mode
   → User can reconfigure or try different network
```

4.5.2 Network Connection Management

**Persistent WiFi Credentials:**
• Credentials stored in ESP32 NVS (non-volatile storage)
• Survives power cycles and reboots
• Automatic reconnection on subsequent startups
• Reset via 5-second button press on device

**Connection Monitoring:**
• Continuous WiFi status checking every 5 seconds
• RSSI (Received Signal Strength Indicator) monitoring
• Automatic reconnection attempts if connection lost
• Exponential backoff for repeated failures (prevents network flooding)

**Dual-Mode Operation:**
```
Normal Mode (WiFi Connected):
- Device operates on home WiFi
- Sends data to Firebase every 3 seconds
- Accessible on local network at assigned IP
- Low power consumption (WiFi sleep modes active)

Fallback Mode (WiFi Disconnected):
- Device enters AP mode after 3 failed reconnection attempts
- User can reconfigure WiFi via captive portal
- Local data logging continues (stored in flash)
- Syncs buffered data once reconnected
```

AquaTrackX was developed to address these challenges by providing an affordable, automated, and self-sustaining water monitoring solution.

2.3 Flow Sensing Technologies

Several technologies exist for measuring water flow:

1. Mechanical Flow Meters: Use rotating elements (turbine, paddle wheel). Advantages include no external power requirement and proven reliability. Disadvantages include mechanical wear and minimum flow requirements.

2. Ultrasonic Flow Meters: Measure transit time of ultrasonic signals. Advantages include high accuracy and no moving parts. Disadvantages include high cost ($200+) and installation complexity.

3. Hall Effect Flow Sensors: Use magnetic field changes from rotating elements. Advantages include low cost, digital output, and good accuracy. Disadvantages include slight mechanical wear over time.

For this project, Hall effect sensors (YF-S201) were selected due to optimal balance of cost, accuracy, and ease of integration.

2.4 Research Gap

While numerous smart water monitoring solutions exist, gaps remain:

1. Most affordable solutions lack automated control features
2. Self-sustaining power solutions are rarely implemented
3. Few systems are optimized for developing country contexts
4. Integration of monitoring, control, and user interface in a single affordable package is uncommon

AquaTrackX addresses these gaps by providing comprehensive functionality at accessible cost point.

3. THEORY

3.1 Water Flow Measurement

Volumetric flow rate (Q) is measured in liters per minute (LPM) and can be calculated from sensor pulse frequency:

Q = (Pulse Frequency × K) / 60

Where K is the sensor calibration factor (typically 2.25 mL/pulse for YF-S201).

Total volume consumed is calculated by integrating flow rate over time:

V = ∫ Q dt ≈ Σ(Q × Δt)

In discrete measurements, this becomes summation of pulses multiplied by pulse volume.

3.2 Hall Effect Sensors

Hall effect sensors operate on the principle that when a current-carrying conductor is placed in a magnetic field perpendicular to the current, a voltage (Hall voltage) develops across the conductor.

VH = (IB) / (net)

Where:
• VH = Hall voltage
• I = Current through conductor
• B = Magnetic field strength
• n = Charge carrier density
• e = Electron charge
• t = Conductor thickness

In flow sensors, a magnetized rotor causes periodic changes in magnetic field, generating pulse output proportional to rotation speed, which correlates with flow rate.

3.3 Firebase Realtime Database

Firebase Realtime Database is a cloud-hosted NoSQL database that allows data to be stored and synchronized in realtime across all connected clients. Data is stored as JSON and synchronized in real-time to every connected client.

Key features:
• Real-time Synchronization: Data updates are automatically pushed to all connected clients within milliseconds
• Offline Capabilities: Data persists locally when device loses connection and automatically syncs when reconnected
• JSON Data Structure: Data stored in simple JSON tree format, easy to read and write
• Security Rules: Built-in authentication and customizable security rules control data access
• Scalability: Automatically scales to handle concurrent connections and data updates

The Firebase SDK provides efficient data compression and caching, making it suitable for IoT applications with limited bandwidth. HTTPS is used for secure data transmission.

3.4 Solenoid Valve Operation

Solenoid valves convert electrical energy into mechanical motion to control fluid flow. When energized:

1. Current flows through solenoid coil
2. Magnetic field is generated
3. Plunger is attracted upward
4. Valve seat opens, allowing flow

Response time depends on:
• Coil inductance and resistance
• Spring force
• Fluid pressure
• Plunger mass

For the 12V valve used, typical response time is 0.5 seconds at rated voltage.

4.2.2 YF-S201 Water Flow Sensor

Hall effect-based sensor with following characteristics:
• Flow range: 1-30 L/min
• Operating voltage: 5-18V DC
• Pulse output: ~4.5 pulses per second per L/min
• Calibration factor: 2.25mL per pulse
• Connection: 1/2" threaded
• Material: Food-grade plastic body, rubber seals

The sensor generates square wave pulses that can be counted using microcontroller interrupts for accurate measurement even during other processing tasks. Flow rate calculation: flowRate (LPM) = pulseCount / 7.5

4.2.3 12V Solenoid Valve

Normally closed (NC) brass valve:
• Operating voltage: 12V DC
• Operating pressure: 0-0.8MPa
• Orifice diameter: 10mm
• Response time: <0.5 seconds
• Connection: 1/2" thread (matches flow sensor)

A relay module is used to control the 12V valve from 3.3V GPIO output of ESP32. The relay provides electrical isolation and can handle the valve's current draw (~500mA).

**Communication Flow:**

2. **Real-time Data Updates** (every 3 seconds):

   - PATCH to `/devices/{DEVICE_ID}/info` with status/lastSeen

3. **History Logging** (every 5 minutes):

4. **Command Processing** (every 2 seconds):
   - GET from `/devices/{DEVICE_ID}/commands/valveControl`
   - Execute command (open/close valve)
   - DELETE command after execution to prevent re-execution

5. **Persistent Storage**:
   - Total litres saved to ESP32 flash (Preferences) every 10L
   - Restored on reboot to maintain accuracy across power cycles

**Error Handling:**
- 3 retry attempts with 1-second delay for failed PUT operations
- Automatic WiFi reconnection with exponential backoff
- Device re-registration after connection recovery
- Offline operation continues with local display updates

4. Valve Control:
   • Automatic shutoff on leak detection
   • Manual control via mobile app (Firebase listeners)
   • Safety timeout (30 min maximum closure)

• Data validation ensures type safety and constraints

4.5 Algorithm Design

4.5.1 Flow Measurement Algorithm

Pseudocode:

FUNCTION measureFlow()
  pulseCount = 0
  ATTACH_INTERRUPT(flowSensor, countPulse, FALLING)
  
  EVERY 1 second:
    DETACH_INTERRUPT(flowSensor)
    flowRate = pulseCount / 7.5  // LPM (YF-S201 calibration)
    
    IF valveState == OPEN AND flowRate > 0.1 THEN
      totalLitres = totalLitres + (flowRate / 60.0)  // Add volume
    END IF
    
    // Save to flash every 10L to prevent data loss
    IF totalLitres - lastSavedTotal >= 10 THEN
      SAVE_TO_FLASH(totalLitres)
    END IF
    
    pulseCount = 0
    ATTACH_INTERRUPT(flowSensor, countPulse, FALLING)
    
    displayFlow(flowRate, totalLitres)
    updateFirebase()  // Send to Firebase via HTTP PUT
END FUNCTION

INTERRUPT countPulse()
  pulseCount = pulseCount + 1
END INTERRUPT

4.5.2 Leak Detection Algorithm

Pseudocode:

FUNCTION detectLeak()
  lowFlowCounter = 0
  leakThreshold = 0.5  // LPM
  leakDuration = 300  // seconds
  
  EVERY 1 second:
    IF flowRate > 0 AND flowRate < leakThreshold THEN
      lowFlowCounter = lowFlowCounter + 1
      
      IF lowFlowCounter >= leakDuration THEN
        TRIGGER_ALERT("Possible leak detected")
        IF autoShutoff_enabled THEN
          closeValve()
        END IF
        sendFCMNotification("Leak detected - valve closed")
      END IF
    ELSE
      lowFlowCounter = 0
    END IF
END FUNCTION

6.3 Limitations

Several limitations were identified during testing:

1. **False Positive Leaks**: 3% false positive rate occurred primarily with slow-filling appliances (washing machines, water heaters). Future versions should implement:
   • Machine learning to recognize usage patterns
   • Adjustable sensitivity settings per household
   • Time-of-day aware thresholds

2. **Flow Range**: YF-S201 sensor minimum flow is ~1 LPM, missing very slow drips. Alternative sensors with lower thresholds could improve detection.

3. **Battery Life Variability**: In low-usage scenarios (<50L/day), micro hydro charging is insufficient, requiring external charging every 20 days. Possible solutions:
   • Solar panel integration
   • Larger battery capacity
   • More aggressive power management

4. **WiFi Dependency**: System requires stable WiFi for optimal operation. Cellular fallback exists but increases power consumption. Future versions could implement:
   • LoRaWAN for low-power long-range
   • Local data logging with periodic sync

5. **Single Point Installation**: System monitors total household usage but cannot identify which fixture is consuming water. Multi-point installations would be needed for detailed analysis.

6.4 Challenges Encountered

Several technical challenges were overcome during development:

**Challenge 1: Pulse Counting Accuracy**
Initial implementation used polling which missed pulses at high flow rates. Solution: Implemented hardware interrupt-based counting with ISR, achieving zero missed pulses.

**Challenge 2: Power Management**
ESP32 WiFi module drew excessive current, limiting battery life to 3-4 days. Solution: Implemented deep sleep modes with wake-on-interrupt, reducing idle consumption from 160mA to 10mA.

**Challenge 3: Data Transmission Efficiency**
Initial design sent updates every second, consuming excessive bandwidth and battery. Solution: Implemented Firebase batch updates (every 3 seconds for real-time data, 5 minutes for history), HTTP PUT/PATCH operations instead of WebSocket, and reduced JSON payload size, reducing data usage by 80% and extending battery life.

**Challenge 4: Water Pressure Effects**
High water pressure caused valve closure to be incomplete in some tests. Solution: Selected higher-rated valve (0.8MPa instead of 0.4MPa) and verified across pressure range.

**Challenge 5: Enclosure Waterproofing**
Early prototype suffered water ingress during outdoor testing. Solution: Upgraded to IP54-rated enclosure with cable glands and sealed all penetrations with silicone.

9.2.1 Main Firmware (Excerpts)

```cpp
// Flow sensor interrupt routine
void IRAM_ATTR flowPulseCounter() {
  pulseCount++;
}

// Main measurement loop
void measureFlow() {
  static unsigned long lastTime = 0;
  unsigned long currentTime = millis();
  
  if(currentTime - lastTime >= 1000) {
    detachInterrupt(FLOW_PIN);
    
    // Calculate flow rate (LPM) - YF-S201 calibration
    flowRate = pulseCount / 7.5;
    
    // Calculate total volume
    if(valveState && flowRate > 0.1) {
      totalLitres += flowRate / 60.0;
    }
    
    // Save to flash every 10L
    static float lastSaved = 0;
    if(totalLitres - lastSaved >= 10) {
      prefs.begin("wm", false);
      prefs.putFloat("total", totalLitres);
      prefs.end();
      lastSaved = totalLitres;
    }
    
    // Reset counter
    pulseCount = 0;
    lastTime = currentTime;
    
    // Check for leak
    checkLeak();
    
    // Update Firebase database
    if(flowRate > 0.1) {
      updateFirebase();
    }
    
    attachInterrupt(FLOW_PIN, flowPulseCounter, FALLING);
  }
}

// Firebase update via HTTP PUT
void updateFirebase() {
  if (!wifiOK) return;
  
  DynamicJsonDocument dataDoc(512);
  dataDoc["deviceId"] = DEVICE_ID;
  dataDoc["flowRate"] = flowRate;
  dataDoc["totalLitres"] = totalLitres;
  dataDoc["valveState"] = valveState ? "OPEN" : "CLOSED";
  dataDoc["status"] = "online";
  dataDoc["batteryPercentage"] = battery;
  dataDoc["timestamp"] = millis();
  
  String dataJson;
  serializeJson(dataDoc, dataJson);
  
  String url = "https://" + FIREBASE_HOST + 
               "/devices/" + DEVICE_ID + "/data.json";
  
  http.begin(url);
  http.addHeader("Content-Type", "application/json");
  int code = http.PUT(dataJson);
  http.end();
}
```

```javascript
// Real-time flow display component
const FlowDisplay = () => {
  const [flowData, setFlowData] = useState({
    rate: 0,
    total: 0,
    valveState: 'CLOSED',
    battery: 0
  });
  
  useEffect(() => {
    const deviceId = 'WM001'; // Get from user's device list
    const ref = database().ref(`/devices/${deviceId}/data`);
    
    // Real-time listener
    const unsubscribe = ref.on('value', snapshot => {
      const data = snapshot.val();
      if(data) {
        setFlowData({
          rate: data.flowRate || 0,
          total: data.totalLitres || 0,
          valveState: data.valveState || 'UNKNOWN',
          battery: data.batteryPercentage || 0
        });
      }
    });
    
    return () => ref.off('value', unsubscribe);
  }, []);
  
  return (
    <View style={styles.container}>
      <Text style={styles.rate}>
        {flowData.rate.toFixed(1)} LPM
      </Text>
      <Text style={styles.total}>
        Total: {flowData.total.toFixed(1)} L
      </Text>
      <Text style={styles.valve}>
        Valve: {flowData.valveState}
      </Text>
      <Text style={styles.battery}>
        Battery: {flowData.battery}%
      </Text>
    </View>
  );
};
```
